## 2. Architecture

```
Browser (same origin, session cookie + CSRF)
  └─ /api/* (server/app.mjs)
       ├─ investigations.mjs ── POST approved n8n webhook (URL + Header Auth from env, host allowlist)
       │      ▲                                     │
       │      └─ /api/investigation-events ◄────────┘ n8n W5/W5p: service key header + per-run token
       ├─ refresh.mjs ──────── Snowflake SQL API (read-only service user, key-pair JWT)
       └─ optimizations.mjs ── Manage adapter (UNAVAILABLE: no external call)
  storage: store.mjs (file store; production needs a managed DB) + append-only audit.jsonl
```

- **Separate responsibilities.** Investigation, refresh and change execution are separate modules with separate roles (`launcher`, `refresher`, `approver`, `executor`). The n8n path has no Manage credential, and an n8n approval is never read as a mutation approval.
- **Result delivery: authenticated callback.** The n8n public API was not inspected for an execution-status endpoint, so no polling endpoint is used or invented. The Webhook responds immediately (`responseMode: onReceived`), and W3 runs with `onError: continueErrorOutput`, so a failure still produces a `failed` event. A run with no callback becomes `timed_out` after `PITT_RUN_TIMEOUT_MINUTES`.
- **Cancellation.** It is not a verified capability. The UI offers **Stop tracking** only, and says it does not stop n8n.

## 3. Contracts (versioned, validated on the server)

- **Launch request `POST /api/investigations`** has the fields `dsp`, `partner_ids`, `network_ids`, `idempotency_key` and `snapshot_id?`. Unknown fields are refused, so a browser cannot send a URL, workflow ID or credential name.
  - The user, environment, workflow and destinations come from the session and the server configuration.
  - The window is `workflow_defined`, because the Investigator anchors its windows on the cut (14 days before, up to 30 after, UTC days).
- **`pitt.launch.v1`** (server → n8n) carries `request_id`, `run_id`, `environment`, `requested_by`, `scope` (`dsp_key`, `partner_ids`, `network_ids`, `timezone: UTC`, `window`), `capabilities`, `options` (`post_to_slack: false`, `create_jira: false`), `snapshot_id` and `callback.token`.
  - The callback token is per run and stored only as a hash. It does appear in the n8n execution data.
- **`pitt.event.v1`** (n8n → server) carries `event_id`, `run_id`, `request_id`, `environment`, `sequence`, `type` (progress or result), `status`, `sent_at`, `execution_id`, `scope` and `result.cases`. The server rejects it if any of these fail:
  - The service key or the run token is wrong.
  - It is a replay (`event_id` is unique).
  - `sent_at` falls outside `PITT_CALLBACK_SKEW_SECONDS`.
  - The scope, environment or run does not match.
  - It is out of order or arrives after a terminal state (recorded, not applied).
  - It exceeds `PITT_MAX_RESULT_BYTES`.
- **`pitt.result.v1`** contains typed cases (`normalizeCase`). Fields the workflow does not give stay null, and nothing is rebuilt from prose. The rules:
  - A `NO DATA` check becomes `unknown`, never pass.
  - Hypotheses are `confirmed: false`, and evidence confidence is kept separate from root-cause confidence.
  - Drafts are `sent: false`.
  - Currency comes from `business_context.revenue_currency`, or from the basis label, and stays unknown when neither has it.
  - The raw item is kept with e-mail addresses redacted.
- **State machines** (`server/contracts.mjs`):
  - Runs: `queued → dispatching → running → succeeded | partial | failed | dispatch_failed | timed_out`.
  - Optimizations: `proposed → manual_required | awaiting_approval → rejected | approved → queued → executing → configuration_verified | partially_applied | verification_failed | outcome_unknown`, plus `stale` and the rollback states. Transitions are enforced in the backend.

### Routes (The Pitt's own; none is an n8n or Manage path)

`GET/POST/DELETE /api/session`, `GET /api/status`, `GET /api/dsp-capabilities`, `GET /api/manage-capabilities`, `POST/GET /api/investigations`, `GET /api/investigations/:runId`, `POST /api/investigation-events` (service only), `POST /api/analytics/refresh`, `GET /api/analytics/refresh/:refreshId`, `GET /api/optimizations`, `POST /api/optimizations/:id/preview`, `POST /api/optimizations/:id/decision`, `GET /api/optimizations/:id/execution`, `POST /api/optimizations/:id/rollback-preview`.

The error contract is `{ error: { code, message, details } }`, with codes `invalid`, `unauthorized`, `forbidden`, `not_found` (also returned for other users' IDs), `duplicate`, `stale`, `unsupported`, `rate_limited`, `upstream_unavailable` and `outcome_unknown`.

## 4. DSP capability registry

The registry is `server/capabilities.mjs`, with seat IDs and names copied from Investigator node 02.

- **Amazon DSP is `supported`.** Seats are 437 AMER Display B, 489 EMEA/APAC Display B, 490 Native B, 491 Video B and 492 CTV B. Each seat is selected separately, so 437 Display never merges with Video or CTV.
- **Beeswax, DV360, TTD, Yahoo and Xandr are `not_integrated`.** They can be selected, but launch is disabled with a reason, and there is no fallback to Amazon. W2 in n8n also refuses any `dsp_key` other than `amazon_dsp`.

## 5. Snowflake refresh

- **Query families.** Only `seat_daily_activity`, `source_watermark` and `connection_events` exist. Each is bind-parameterised and limited to the selected networks and seats, with a window of at most 92 days. Nothing in SQL comes from the browser.
- **Validation.** Duplicate keys (fan-out), rows outside the scope, missing days (listed), and nulls kept as nulls. RPMBr is null when bid requests are 0.
- **Provenance and promotion.** Each dataset records its query ID (`statementHandle`), executed-at time, row count, coverage and source watermark. A new snapshot is promoted only when every dataset is complete. A partial or failed refresh is stored and labelled, but the last complete snapshot stays current and its dependent calculations are blocked.
- **Stale approvals.** Promoting a snapshot makes pending approvals on the same network `stale`, which forces a new preview.
- **Scope.** The refresh is read-only, and it never launches, approves or executes anything.

## 7. Connecting the site to n8n dev

The non-secret settings are already in `.env.n8n-dev.example`: n8n dev host, W1 path `the-pitt-launch-f95a59df`, header names, workflow ID and launch budget.

1. Generate two secrets on your machine. Don't paste them into chat:
   ```bash
   openssl rand -base64 32   # launch key
   openssl rand -base64 32   # callback key
   ```
2. In n8n dev, create two **Header Auth** credentials and select them on the nodes:
   - Name `x-pitt-launch-key` with the launch key, selected on **W1**.
   - Name `x-pitt-callback-key` with the callback key, selected on **W5** and **W5p**.
3. In W5 and W5p, replace `https://REPLACE-WITH-APPROVED-PITT-HOST` with a site address that n8n dev can reach. A laptop's `localhost` is not reachable: use the deployed dev site, or a tunnel approved for the purpose.
4. Copy `.env.n8n-dev.example` to `.env.n8n-dev`. Fill in the two keys, `PITT_SESSION_SECRET` and `PITT_USERS_JSON`. Then run `npm run api:n8n-dev`.
5. In the n8n editor, press **Listen for test event** on W1. The Test URL only accepts a call while that is active, and the Production URL needs the workflow published, which it is not. Then press **Launch investigation** on the site.

Every launch uses one of the project's 25 n8n executions per week. The site path posts nothing to Slack and creates no Jira ticket.
